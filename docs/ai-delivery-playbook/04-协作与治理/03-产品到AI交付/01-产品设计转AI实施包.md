# 产品设计转 AI 实施包

- 模板编号：`DIALOG-HANDOFF-01`
- 主要使用者：产品经理、业务负责人
- 共同完成者：AI；技术负责人复核技术部分
- 状态：可用试点；待跨项目验证

## 这张卡解决什么

产品材料适合人评审，却不一定能直接执行。实施包把“做什么”补成“在当前哪个项目、只做哪一步、允许哪些动作、怎样证明完成”。**产品人员不负责把这些技术字段填完；AI 应先读取当前项目并生成草案。**

## 人需要提供什么

只需四类信息：

1. 已经确认的产品材料或附件；
2. 本轮希望拿到的一个业务结果；
3. 明确不做什么；
4. 用什么可见结果做产品验收。

项目 slug、工作区、分支、Git 提交、代码目录、相似模块、Skill、测试命令和发布能力由 AI 自行读取。AI 查不到时标记技术阻塞，不要求产品猜。

## 可直接复制给 AI：生成实施包草案

```text
请把我已经确认的产品材料整理成“当前阶段 AI 实施包”。本轮先生成和核对合同，不立即发布。

产品材料：{{文件、附件、截图或文字描述}}
本轮想拿到：{{一个可验收结果}}
本轮不做：{{列表；不知道可空}}
产品验收：{{用户能看到或完成什么}}
允许动作：{{不知道时写“请先建议”}}

请自行读取并代填：当前项目/工作区、AGENTS 与项目上下文、分支/提交/工作区状态、相关源码和相似实现、需要的 Forge/Harness Skill、现有测试与发布合同。

输出实施包草案时分开：
1. 人已确认的业务事实和决定；
2. 你从项目读取的技术事实及来源；
3. 暂定假设和验证方法；
4. 必须由人决定的事项。

只问最多 3 个会改变业务结果、范围、权限或验收的问题，并给推荐。类名、表名、接口风格、构建和部署方式转技术复核，不作为产品选择题。材料冲突时先给差异表，不进入实现。
```

## AI 生成的实施包必须包含什么

以下是 AI 的输出合同，不是产品填写清单：

| 部分 | AI 要写清楚 | 谁确认 |
|---|---|---|
| 身份与基线 | 项目、任务编号、工作区、分支、提交、已有改动 | AI 查证，技术抽查 |
| 当前阶段 | 需求/设计/前端/后端/联调/测试/发布中的一个 | 产品确认结果，AI 约束阶段 |
| 业务合同 | 目标、用户、规则、范围、非目标、产品验收 | 产品/业务 |
| 技术事实 | 相关文件、相似实现、组件、接口、表、Skill、约束 | AI 查证，技术复核 |
| 输入与输出 | 将读取什么、修改什么、产生哪些文件或结果 | AI；技术复核 |
| 动作权限 | 只读/改文档/改代码/测试/已批准发布，以及禁止事项 | 有权限的人确认 |
| 验证分工 | 产品 UAT、自动测试、技术复核、Runner 证据分别是什么 | 对应角色 |
| 停止条件 | 冲突、未知改动、越权、测试/迁移失败和外部阻塞 | AI 必须执行 |
| 不能声称 | 当前阶段未覆盖的完成状态 | AI 如实报告 |

## AI 可以自动推进到哪里

- 只读分析和实施包草案：材料足够时直接完成，不反复让人确认低风险细节；
- 修改文档或代码：必须在本轮允许动作和范围内；
- 测试：只运行约定的、可恢复的当前项目测试；
- 发布：只有实施包明确写明目标项目、环境、批准版本、范围、窗口和授权时，才能进入独立发布卡与 Runner 门禁。

一次“允许改代码”不能继承成“允许迁移或发布”。进入下一阶段时生成新版本实施包或明确更新动作级别。

## 人工验收这份实施包

产品人员只检查：AI 是否正确理解目标、范围、非目标和产品验收；有没有替产品发明业务规则。技术人员检查：项目、基线、影响文件、Skill、测试和风险是否真实。执行人员检查：允许动作和停止条件是否唯一。

如果任何一方还必须回看整段历史对话才能知道“现在做什么”，实施包没有通过。

## 停止条件

项目或版本不唯一、权威材料互相冲突、核心业务决定缺失、数据/权限责任不清、工作区有归属不明改动时，只生成阻塞和建议，不进入实现。实施包不得包含 API Key、口令、真实敏感数据，也不授权跨项目、宿主机或基础设施操作。
