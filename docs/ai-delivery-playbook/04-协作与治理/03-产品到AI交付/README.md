# 产品到 AI 交付

本目录解决的不是“怎样设计产品”，而是产品方案已经形成后，业务、产品和实施人员怎样把它交给 AI，并通过可见对话稳定推进到实现、验证和受控发布。

当前阶段为 **可用试点**：内容来自 `forge-base` 的真实对话、偏航、修复和发布证据，尚未经过多个客户项目的规模化验证。它不能证明任何非技术人员已经可以无人值守交付。

普通产品/业务人员优先使用“安全试用卡 + AI 代填的实施包”，不需要依次阅读本目录六份文档。缺陷演进、推广指标和产品路线图属于维护者工作。

## 为什么需要单独一层

一份适合人评审的 PRD，并不天然等于 AI 可以执行的任务。AI 还需要知道当前项目、权威文件、唯一阶段、允许动作、禁止事项、输出位置、验收证据和停止条件。缺少这些运行合同后，即使产品设计正确，也容易出现范围扩张、重复造能力、把检查当修复、把发版当环境初始化或无证据宣称完成。

## 推荐顺序

1. 产品/业务人员第一次参与试用时先读 [产品人员 Harness 安全试用卡](06-产品人员Harness安全试用卡.md)，明确负责什么、哪些技术动作必须停止；
2. 使用 [产品设计转 AI 实施包](01-产品设计转AI实施包.md)，把已批准产品产物转成机器可执行的当前阶段合同；
3. 使用 [阶段化对话与授权语义](02-阶段化对话与授权语义.md)，约束每轮对话的动作边界和状态回报；
4. 出现偏航或重复问题时，使用 [对话缺陷反馈与模板演进](03-对话缺陷反馈与模板演进.md)，把证据转成项目修复或通用模板候选；
5. 准备扩大使用人群时，使用 [规模化推广与运营指标](04-规模化推广与运营指标.md)，分批推广并度量真实任务结果；
6. 评审 Harness 对话产品本身时，使用 [Harness 对话产品能力缺口与路线图](05-Harness对话产品能力缺口与路线图.md)，区分文档可补问题和必须由产品/平台实现的问题。

## 固定边界

- 聊天记录不是业务规则的唯一权威，稳定决定必须回写 PRD、设计、代码或运行证据；
- “继续”“修复”“验证”“发版”只继承当前已确认阶段，不能自动扩权；
- 提示词只能表达流程，不能代替权限、测试、静态检查、Runner 和浏览器验收；
- 任何对话经验都先形成带证据的候选，不自动写入通用模板、项目 Memory 或平台能力；
- 大规模推广前先证明任务成功率、返工率、越权率和恢复能力，不以消息数或 Token 消耗证明价值。
