# 对话缺陷反馈与模板演进

- 模板编号：`DIALOG-FEEDBACK-01`
- 面向角色：使用者、产品运营、实施负责人、平台维护者
- 状态：可用试点；用于收集候选，不自动晋升平台能力

## 目标

把“这次 AI 又做错了”的口头抱怨，转成可定位、可复现、能决定落点的产品反馈。反馈的终点不一定是新增提示词：它可能应该修 PRD、更新现有任务单、增加确定性门禁、调整 Harness 产品界面，或修改版本化平台能力。

普通使用者只需提交“我说了什么、希望怎样、实际怎样、造成什么影响”以及截图/会话引用。项目、版本、阶段、权限、日志和提交由维护 AI 从可见证据补齐；缺失项标记为缺口，不能要求使用者填写完整缺陷表后才受理。

## 缺陷反馈卡

```text
请把下面的 AI 对话问题整理为缺陷反馈卡。只整理和分类，不自动修改通用模板、Memory、平台代码或运行环境。

项目/任务：{{AI 从当前会话提取；跨会话时由人提供}}
发生时间与会话：{{能提供就写；AI 先读取可见记录}}
使用者角色：{{产品/业务/实施/测试/运维}}
所处阶段：{{需求/设计/实现/测试/发布/运营}}
用户原始表达：{{尽量保留短句}}
预期行为：{{希望 AI 做什么和不做什么}}
实际行为：{{可观察事实}}
影响：{{返工、风险、时延、数据或协作影响}}
证据：{{文件、请求、日志、截图、提交、运行状态}}
当时权限与边界：{{AI 从任务合同/会话提取，用户只补充外部授权}}

请输出：
1. 缺陷编号、标题、严重度和影响用户；
2. 事实、推测和缺失证据；
3. 根因层：业务材料 / 实施包 / 对话模板 / 产品交互 / Harness 客户端 / 平台能力 / 模型或供应商 / 环境；
4. 临时恢复办法，以及是否已恢复；
5. 最合理的永久落点和理由；
6. 是否可确定性检测，若可以给出输入、失败条件和回归；
7. 是否具有跨项目复用价值；
8. 负责人、下一步、复测条件和当前状态；
9. 不能声称的事项。
```

## 永久落点判定

| 问题类型 | 首选落点 | 不应怎样处理 |
|---|---|---|
| 某项目业务事实缺失或冲突 | 当前 PRD、决定或实施包 | 写成所有项目通用规则 |
| 用户经常不知道怎样表达同一任务 | 回填现有任务单或对话模板 | 每次新建一个近义 Prompt |
| AI 能稳定被规则引导，但步骤容易遗漏 | Skill/任务编排候选 | 只在某个会话临时提醒 |
| 输入和失败条件可以机器判断 | 测试、静态检查器或 Runner 门禁 | 用自然语言声称“已经检查” |
| 页面没有展示项目、阶段、权限或进度 | Harness/门户产品需求与验收 | 要求用户背诵更多系统提示词 |
| 客户端、上传、历史、模型设置等运行缺陷 | 版本化镜像、模板、幂等升级和回归 | 热改一个容器后声称所有副本具备 |
| 一次模型失败或供应商限流 | 会话证据、降级策略和可用性指标 | 推导永久模型能力排名 |

## 从反馈到正式资产

```text
真实问题
  → 原始证据和项目缺陷卡
  → 恢复当前项目
  → 提炼“症状—根因—固定做法—最低验证”
  → 优先回填已有任务单
  → 确定性门禁/产品能力候选
  → 代表性项目复测
  → 版本化发布和推广
```

同一根因只维护一个主条目，新证据追加来源。未经评审的反馈保持候选状态；修改项目文件不等于授权写入 MCP Memory、Task、checkpoint 或其他受控状态。

## 隐私与证据边界

反馈卡不复制口令、API Key、完整客户数据、长对话或无关工具输出。优先记录会话引用、时间、文件路径、提交和哈希。用户原始表达只保留定位问题所需的最短片段。

## 人工验收

维护者应能根据反馈卡复现问题，并明确回答“现在修哪里、为什么、怎样证明以后不再发生”。如果结论仍是“让 AI 注意一点”，说明尚未找到可复用解决办法。
