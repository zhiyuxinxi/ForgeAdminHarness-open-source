# 多对话 Git 合并与数据库版本

> 公开版阅读提示：本文保留原有日期的维护背景与样本，其中内部部署和验收记录不代表当前公开版状态。未随公开包提供的材料只作历史来源说明，不是上手前置阅读。

## 给产品人员的结论

多人和多个 AI 对话可以并行开发，但项目最终只有一条集成线、一套数据库迁移顺序和一个串行发布互斥门禁。当前不是自动等待队列：第一个请求获得项目发布锁；第二个同时请求会收到可重试的 `TASKSPACE_RELEASE_IN_PROGRESS`，等前一个完成后重新 preflight 和发版。账号用于确认人员，独立对话用于隔离工作过程，Git commit 才是代码版本，Runner 发布记录才是生产版本。

## 代码怎样合并

每个新对话获得独立 TaskSpace、clone 和任务分支。准备发布时，候选必须满足：工作区 clean、全部交付内容已提交、包含项目最新集成 HEAD、测试完成。若其他对话已经推进集成线，后完成者必须在自己的 TaskSpace 中 fetch/rebase 或 merge，显式解决冲突并重新测试。

Broker持有项目唯一发布锁，先完成候选准备检查，再接受fast-forward晋升；顺序修复见TODO-042（历史维护材料，未随公开包提供）。启用私有 Git 远端后，Broker 还会先确认远端分支与服务器集成 HEAD 相等，把候选普通 fast-forward 推送到远端并复核，再推进服务器集成线。任何远端漂移、推送失败或旧基线都会阻断发布，系统不会用最后写入覆盖前序结果。

同一项目的并发发布不会在服务器内长期挂起，也不会保留一个可能过期的自动队列项；被拒绝的发起人必须在锁释放后重新检查最新集成 HEAD。不同项目有各自的 Broker、发布锁、数据库和应用栈，可以并行发布。

## 数据库怎样维护

数据库不是每个分支一套。每个项目只有独立主库、固定 `_test` 测试库以及独立运行/测试 Redis DB。分支开发阶段把数据库变化写成版本化 Flyway 文件并随代码提交；真实数据库只由项目 Runner 在串行队列中执行。

若两个分支都选择了同一个下一迁移版本，先进入集成线的候选占用该版本。后完成者同步最新集成线后必须把自己尚未发布的迁移顺延，重新检查依赖并重跑测试。已经进入集成线或执行过的迁移禁止修改、删除或覆盖，只能新增前向修复迁移。

候选先使用同一候选镜像迁移 `_test`。Runner 在迁移前登记健康快照和 `migration-pending`；失败或中断后标记 `restore-required`，下一次修正版先恢复已验证快照再重试。只有测试库迁移、测试和构建通过，才允许主库迁移和应用切换。

## 当前边界

- 代码开发可以并行，项目集成、测试数据库迁移和生产发布必须串行；
- 私有 GitLab 是异机 Git 历史和远端一致性边界，不替代测试、数据库快照或项目备份；
- 当前尚无每任务数据库，数据库重型需求可能排队；只有 Forge 迁移能从可信基线完整重建后，才适合引入临时 schema/数据库 clone；
- 候选准备失败不应先晋升。准备检查通过后仍可能在数据库、部署或健康阶段失败，此时已经推进的Git与实际生产版本分别报告，按已有恢复流程处理，不能以一次准备检查保证整个发布必然成功。

## 产品验收时应询问

1. 当前生产版本对应哪个 release、commit 和镜像 ID？
2. 该 commit 是否同时存在于项目私有 Git 远端？
3. 候选是否基于最新集成 HEAD，冲突由谁解决并重新测试？
4. 是否包含 Flyway 迁移，版本号是否与最新集成线冲突？
5. `_test` 快照、迁移结果、主库影响和失败恢复状态是什么？
6. 发布失败时生产是否仍运行上一成功镜像，健康检查是否重新通过？
