# 低代码或代码开发选择

模板编号：`FA-ARCH-01`  
目标：在进入实现前选择最小但可持续的交付方式

## 谁做决定

业务人员提供复杂度、变化频率、期限和不可接受风险；AI 从当前部署和源码核对低代码/代码生成能力，技术负责人决定实现路径。不要把“低代码还是 Java/Vue”作为产品人员必须回答的技术选择题。

## 判断维度

| 更适合低代码配置 | 更适合生成代码/定制代码 |
|---|---|
| 标准字段、列表、表单、简单关系 | 复杂事务、批量算法、特殊性能要求 |
| 权限和流程可由平台配置表达 | 需要自定义鉴权、外部集成或补偿 |
| 业务变化主要是字段和页面 | 业务规则频繁且需要单测/版本治理 |
| 可接受平台运行时约束 | 需要独立 API 合同和精确发布控制 |

## 可直接复制给 AI

```text
请为 {{业务功能}} 比较 Forge Admin 低代码实现、官方 CRUD 代码生成和定制代码三种路径。先基于当前固定版本源码/实际启用模块核对能力，不要根据产品宣传假设全部可用。

业务复杂度：{{对象、规则、流程、集成}}
数据量与性能：{{业务量级由人描述；技术指标由 AI/技术补充}}
权限、流程、导入导出：{{要求}}
预期变化频率：{{说明}}
团队接手能力与上线时限：{{人提供现实约束}}

对每种路径输出：能覆盖的需求、不能覆盖的需求、要配置/生成/手写的资产、测试与发布方式、迁移/退出成本、主要风险。
给出推荐路径和触发“从低代码升级到代码”的明确条件。
不要用开发天数作为唯一依据；重点比较业务正确性、可测试性、权限、可观测性和长期维护。
```

## 推荐原则

先选能完整表达业务边界且可验收的最低复杂度方案。若低代码需要大量绕过、隐式脚本或无法覆盖数据权限/事务，就应转代码；若只是标准 CRUD，则不应为了“灵活”手写一整套页面和接口。

## 停止条件

当前部署是否启用低代码运行时、对象设计器和发布链路不清楚时，先做只读能力验证；不得承诺“一句话上线”。
