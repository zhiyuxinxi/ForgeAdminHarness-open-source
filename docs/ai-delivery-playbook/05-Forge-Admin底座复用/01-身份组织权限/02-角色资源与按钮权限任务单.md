# 角色、菜单、按钮与 API 权限任务单

模板编号：`FA-IAM-02`  
平台依赖：`SysRole`、`SysResource`、角色资源关系、Sa-Token、操作日志  
证据：Forge Admin v1.1.2 固定源码（S1）

## 目标

把业务动作映射为可配置、可审计的资源，而不是只做一个菜单或只隐藏前端按钮。一个完整动作通常同时涉及页面入口、按钮显示、后端权限和操作日志。

## 人与 AI 的分工

业务人员只确认“哪个角色能做哪个动作”和至少一个应该拒绝的例子。AI 自行读取资源树、权限用法、相似 migration 和官方 Skill，生成权限码与资源实现；技术/安全人员复核后端鉴权和授权数量。产品不需要知道 `sys_resource`、`client_code` 或 migration 唯一键。

## 可直接复制给 AI

```text
请为 {{业务模块}} 设计并实现 Forge Admin 权限资源。先读取现有相似菜单/resource migration、角色接口、前后端权限用法和官方 CRUD Skill。

业务角色：{{列表}}
业务动作：{{查询详情/新增/编辑/删除/批删/导入/导出/提交/审核等}}
页面入口与层级：{{说出业务菜单位置；实际资源树由 AI 查证}}
高风险动作：{{批量、导出、审批、配置、删除等}}

输出并在获准时实现：
1. 角色—业务动作矩阵，默认拒绝；
2. 目录、菜单、按钮、API 资源树和稳定权限码；
3. 前端按钮控制与后端独立鉴权点；
4. 详情、批量、导入导出、流程动作是否需要独立权限；
5. OperationLog 模块、操作类型和审计内容；
6. sys_resource 与角色授权的幂等 migration，必须包含 tenant_id=1、client_code 等现有唯一键需要的字段；
7. 有权限、无权限、只见按钮但接口拒绝、伪造 ID、角色变更后的测试。

不要擅自把所有新资源授予所有角色；只可按已批准角色矩阵初始化。输出实际资源数量和授权数量的核对 SQL。
```

## 验收清单

- 菜单可见不等于按钮可用，按钮可见不等于 API 放行；
- 查询、导出、删除、审批等风险不同，应分别授权；
- migration 必须按当前唯一键字段做 `NOT EXISTS`，不能只按 `perms` 猜测资源唯一；
- 角色删除、停用、解绑后，权限缓存和会话行为有明确验证；
- 超级管理员行为与普通租户角色行为分别测试。

## 停止条件

角色矩阵没有业务负责人确认、权限码与已有资源冲突、目标客户端 `client_code` 不清楚时，只生成评审稿，不写默认全量授权。
