# Kimi K3 与 DeepSeek V4 模型协作

本目录不做价格分析，也不做抽象“谁更聪明”的排名，只记录本项目真实发生的工作和由此形成的可复用接力方式。

这是实施负责人和平台维护者资料，不是产品人员的必选流程。普通使用者只描述任务和验收；协调 AI 根据当前可用模型与证据决定是否接力，并自动生成交接包。不要要求产品人员先研究模型分工。

## 本项目已验证分工

- Kimi K3：适合放在“阅读背景、形成首稿、生成边界明确的原子产物”位置；本次实际生成了规格草案和数据库 migration 首稿。
- DeepSeek-V4-Flash：本次实际承担“审核首稿、补完实现、测试、集成与发布证据”；它不是只审查，也写了后端和前端。

这只是当前项目证据，不是永久绑定。未来如果会话证据显示另一种分工更有效，可以调整路由，但同一任务的输出合同和验收门禁不变。

## 推荐用法

1. 让 Kimi 使用 [首稿任务单](01-Kimi-K3首稿任务单.md) 产出一个有边界的设计或 migration 草案；
2. 人工确认业务语义，不直接把首稿当最终版本；
3. 用 [双模型接力包](03-双模型接力包.md) 把事实、文件和未决项交给 DeepSeek；
4. DeepSeek 使用 [实施审核任务单](02-DeepSeek-V4实施审核任务单.md) 先审查、再补完、再验证；
5. 发布仍走独立门禁，不因模型已经修改代码而自动授权。

不要同时让两个模型无边界地重读整个仓库、各做一套完整实现。那会产生重复上下文、合同漂移和很高的复核成本。
