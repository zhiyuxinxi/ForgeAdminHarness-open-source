# 权限与数据范围设计

## 何时使用

涉及多角色、租户、部门、项目、负责人或敏感操作时使用。只有单一可信角色的临时工具也应明确当前信任边界。

Forge Admin 落地时进一步使用 [身份组织权限目录](../../05-Forge-Admin底座复用/01-身份组织权限/README.md)，分别处理任职、功能权限和数据范围，不能合并成一个“角色字段”。

## 使用分工

业务人员用具体例子说明“谁在什么情况下能看哪几条、能做什么、什么必须拒绝”。AI 把例子转换成矩阵并从项目读取认证/RBAC/数据范围机制；技术与安全人员复核后端鉴权和反向测试。产品不填写权限码、拦截器或查询过滤实现。

## 可直接复制给 AI

```text
请为 {{功能范围}} 设计可落地的权限与数据范围，不写“管理员拥有全部权限”后结束。

角色：{{角色及职责}}
业务动作：{{查询/新增/修改/删除/审核/导入/导出等}}
数据归属：{{租户/组织/项目/负责人/本人}}
敏感操作与字段：{{列表}}
现有认证、RBAC 和数据权限机制：{{由 AI 从当前项目读取并注明来源}}

输出：
1. 角色—动作权限矩阵；
2. 角色—数据范围矩阵；
3. 页面、按钮、接口和查询过滤的控制点；
4. 新增、修改、删除、批量、导入导出、审批的差异规则；
5. 跨租户/跨组织、越权 ID、伪造身份、缓存和后台任务风险；
6. 审计事件、日志字段和告警建议；
7. 权限码建议及与现有规范的映射；
8. 正向与反向验收用例。

后端必须独立鉴权和约束数据范围，不能依赖前端隐藏。未知的信任边界标为阻塞项。
```

## 人工验收

逐个角色回答“能否看、看哪些、能否改、何时不能改、能否导出”。至少验证一个越权 ID 和一个跨范围查询会被拒绝并留下可审计结果。

## 停止条件

认证来源、租户边界或敏感数据授权不清楚时，不生成默认放行实现。
