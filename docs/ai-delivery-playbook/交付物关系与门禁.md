# 交付物关系与门禁

AI 交付不是“一句话生成系统”，而是一条可追踪的交付链。每个阶段的输出都是下一个阶段的输入，发现冲突时应回到最近的业务决定，而不是让后续代码掩盖问题。

这张图是协调 AI 和负责人检查进度的地图，不是要求产品人员亲自编写所有交付物。每一步都应标明“人确认什么、AI 自动生成什么、技术/测试复核什么”。

## 主链路

```text
业务问题
  ↓ 目标、用户、成功标准
产品简报 / 需求澄清
  ↓ 范围、非目标、业务规则
PRD / 用户故事 / 验收标准
  ↓ 项目、版本、当前阶段、允许动作、输出与停止条件
AI 实施包 / 当前阶段对话合同
  ↓ 术语、对象、状态、权限
领域模型 / 库表 / 字典 / 流程
  ↓ 页面合同、接口合同
前端实现 ↔ 后端实现
  ↓ 测试结果、迁移证据、差异清单
UAT 与发布准入
  ↓ 审批、版本、回退点
受控发布
  ↓ 指标、日志、用户反馈
上线观察与迭代
```

## 八个不能跳过的门禁

| 门禁 | 必须回答的问题 | 不满足时怎么办 |
|---|---|---|
| 目标门禁 | 用户是谁、解决什么问题、怎样算成功？ | 停在产品简报，不进入实现 |
| 范围门禁 | 本次做什么、不做什么、受哪些约束？ | 标记待决定项，由负责人裁决 |
| 业务门禁 | 正常、异常、权限、状态和数据归属是否明确？ | 补业务规则与验收标准 |
| 交接门禁 | 已批准产品产物是否转换为带项目、版本、阶段、输入输出和停止条件的 AI 实施包？ | 不进入 AI 执行，先补实施包 |
| 执行门禁 | 当前对话是只读、改文档、改代码、测试还是发布，权限是否可见且唯一？ | 停止扩展动作，重新建立阶段合同 |
| 设计门禁 | 页面、接口、表、字典、流程是否使用同一术语和状态？ | 输出冲突表，先统一合同 |
| 质量门禁 | 测试、构建、迁移、权限和回归证据是否真实可复核？ | 不能声称完成或申请发布 |
| 发布门禁 | 是否有审批、版本、影响范围、回退点和观察方案？ | AI 只能生成计划，不能执行 |

## 事实、假设和决定必须分开

- **事实**：来自用户确认、项目文件、数据库结构、接口、日志或测试的可验证内容；
- **假设**：为了继续分析暂时采用、但尚未确认的判断；
- **决定**：有明确责任人和日期的选择；
- **待办**：尚未完成的动作；
- **证据**：能支持“已完成”的命令输出、测试报告、变更记录或验收结果。

AI 的输出如果混合这五类内容，产品经理很难判断哪些已经确定。所有场景任务单都会要求分栏表达。

## 完成的定义

“产品已确认”“实施包已建立”“代码生成”“测试通过”“已经发布”是不同状态。只有满足当前阶段的交付物、验收清单和证据要求，才能声明该阶段完成；任何一个阶段完成都不自动代表整个项目完成。
