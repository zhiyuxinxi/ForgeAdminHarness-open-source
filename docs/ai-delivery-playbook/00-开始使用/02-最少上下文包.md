# 最少上下文与 AI 代填规则

Policy marker: `PLAYBOOK_AI_PREFILL_V1`.

上下文不是由人一次填完的长表，而是人和 AI 分工建立的当前任务事实。原则是：**人说业务，AI 查项目；人做业务决定，技术证据由系统和专业人员产生。**

## 产品/业务人员最多提供什么

只提供你真实知道、且会改变业务结果的内容：

- 谁遇到什么问题，当前怎样处理；
- 希望发生什么可观察变化；
- 业务规则、正反例和不可接受结果；
- 本轮范围、明确不做和时间/合规约束；
- 截图、原型、会议记录或样例数据的位置；
- 谁能确认业务决定和产品 UAT。

不要提供口令、API Key、完整客户数据。也不要为了填写模板猜测表名、接口、类名、分支、提交、构建命令、数据库迁移或服务器操作。

## AI 必须自己读取什么

在当前权限允许的范围内，AI 应自行确认并注明来源：

- 当前项目、工作区、分支、提交和已有改动；
- `AGENTS.md`、项目上下文、相关 Skill 和运行边界；
- 现有相似页面、组件、接口、实体、表、迁移和测试；
- 当前技术栈、命名、权限、字典、流程和发布合同；
- 能执行的验证命令，以及哪些能力当前不可用。

查不到就写“未发现/无权读取/需要技术人员确认”，不能改为让产品人员猜答案。

## 三类内容怎样处理

| 内容 | AI 怎么做 | 谁最后确认 |
|---|---|---|
| 可以从项目查到 | 自动读取、引用路径或证据 | AI 自检，技术人员抽查 |
| 需要技术判断 | 给推荐、权衡、验证和回退 | 技术负责人 |
| 需要业务决定 | 用业务语言给选项、影响和推荐 | 产品/业务负责人 |

每轮最多向普通使用者提出 3 个会改变目标、范围、权限、业务规则或验收的问题。低风险细节由 AI 按项目规范暂定，并在结果中标明。

## 可直接复制给 AI：先替我完成能完成的部分

```text
请建立本轮上下文草案。所有从当前项目能够读取的信息由你自行读取并注明来源，不要让我填写技术字段。

我的原始描述：{{原话或附件路径；不知道的不用补}}
我能确认的业务事实：{{可留空}}
我明确不接受的结果：{{可留空}}

请输出四栏：
1. 人已提供并确认；
2. 你从项目查到；
3. 暂定假设及验证方法；
4. 必须由人决定。

需要我决定时，用“发生了什么 / 业务影响 / 推荐 / 其他选项 / 不决定的后果”表达。技术路径放在后置说明，转给技术复核。第一轮最多问 3 个问题。
```

## `{{占位符}}` 的真实含义

- 它是提示“这里可能需要信息”，不是必填题；
- 明确知道就替换，不知道可删除、留空或写“不知道”；
- 项目中已有的信息由 AI 补；
- 会改变业务结果的未知项由人决定；
- 只影响实现细节的未知项由 AI 提案、技术复核。

如果一张任务单仍要求产品人员先填 Git 提交、接口路径、数据库工具或测试命令，应把这些字段交给 AI 预检，而不是阻塞业务人员开始。
