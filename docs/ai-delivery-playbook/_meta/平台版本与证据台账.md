## 重要固定契约

- 业务实体优先继承 `TenantEntity`，不要重复声明继承来的租户与审计字段；
- 审计字段基线为 `id`、`tenant_id`、`create_by`、`create_time`、`create_dept`、`update_by`、`update_time`；
- 查询 SQL 放 Mapper XML；分页字段使用 `pageNum/pageSize`；
- 生成型 CRUD 使用 POST-safe 合同；
- 字典写入 `sys_dict_type/sys_dict_data`，前端通过平台组件读取，不能在页面硬编码；
- 需要“删除后可重新使用业务编码”时，逻辑删除采用主键墓碑：`del_flag BIGINT/Long`，删除值为当前 `id`；
- migration 必须新增版本、显式列名、幂等防重复；内置租户数据使用 `tenant_id=1`；
- 工作流由真实 BPMN 设计器与表单/绑定配置驱动，不得用一个模拟状态字段冒充流程引擎。

## 产品到 AI 对话运营证据

| 真实现象 | 已确认结论 | 证据等级 |
|---|---|---|
| 用户只说“发版”，模型曾把应用发布理解为重新部署 MySQL/Redis | 常用动词需要绑定当前项目、阶段、允许动作和固定基础设施边界；提示词说明与 Runner 硬门禁缺一不可 | S3 |
| 模型因陈旧运行契约反复向用户索取 Runner token | 内部服务身份不能成为对话输入；实时契约和 capability socket 应对模型隐藏秘密 | S3 |
| 用户要求交付必须由 Harness 对话中的模型完成并保留可见历史 | 正常项目实现/发布的产品闭环应是“业务人员—Harness 模型—工作区—证据”，Codex/SSH 只负责平台能力和独立验收 | S4/S3 |
| 历史一次加载、手动分页、浏览器上传和远程设置页先后暴露可用性问题 | 对话产品验收必须覆盖真实远程浏览器、长历史、附件上下文、客户端能力判定和控制台，而不只测 API 200 | S3 |
| 多人使用期间不能任意重启 Harness 或清理未知工作区 | 会话、任务、操作者、分支/提交和维护窗口需要成为可见的协作边界 | S3 |

这些证据支持 `DIALOG-HANDOFF-01`、`DIALOG-CONTROL-01` 和 `DIALOG-FEEDBACK-01` 进入可用试点，不证明跨客户、跨团队或无人值守规模交付已经成熟。详细来源见 真实交付踩坑与跨项目复用经验（历史维护材料，未随公开包提供） 和 [产品到 AI 交付](../04-协作与治理/03-产品到AI交付/README.md)。
