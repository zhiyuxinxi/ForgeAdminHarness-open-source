# 阶段交付物与评审门禁

## 推荐顺序

1. 用产品简报确认机会和目标；
2. 用澄清工作坊处理会改变范围或规则的问题；
3. 编写 PRD，明确范围、流程和业务规则；
4. 补充用户故事、异常和验收标准；
5. 对重大方案做比较，对候选需求排优先级；
6. 由业务负责人确认产品基线；
7. 使用 [产品设计转 AI 实施包](../04-协作与治理/03-产品到AI交付/01-产品设计转AI实施包.md) 生成当前阶段的项目、版本、授权和验收合同后，才进入系统和实现设计。

## 产品评审清单

| 维度 | 必须明确 | 常见失败 |
|---|---|---|
| 目标 | 用户、问题、预期变化、指标 | 把“做一个功能”当目标 |
| 范围 | 本期、后续、明确不做 | 默认 AI 把所有相关能力一起做 |
| 规则 | 触发条件、状态、异常、撤销 | 只描述正常路径 |
| 权限 | 谁能看、建、改、删、审、导出 | 只写“需要权限控制” |
| 数据 | 来源、归属、敏感级别、留存 | 用真实数据样例直接粘贴给模型 |
| 验收 | Given/When/Then 或可观察结果 | 用“体验良好”“正常运行”验收 |

## 进入下一阶段前必须签字的事项

负责人至少确认：核心范围、关键业务规则、角色权限、成功指标、不可接受风险。技术方案、字段命名和实现细节可以继续演进，但不能反过来静默改变已确认的业务决定。产品确认只确认业务基线，不等于授权 AI 修改代码、测试、迁移或发布；动作授权写入对应阶段实施包。
