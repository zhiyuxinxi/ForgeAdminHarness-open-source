# 用户故事与边界验收

## 何时使用

PRD 主体已形成，但需要把功能拆成用户视角的可交付单元，并补齐异常、权限和边界值时使用。

## 使用分工

产品人员只确认角色目标、业务规则和可观察结果。AI 从 PRD 中提取状态、字段和已有权限描述，主动补齐边界草案；研发和测试再复核并发、接口和数据副作用。不要让产品人员先填写一张技术边界清单才能开始。

## 最少输入

用户角色、功能范围、业务规则、状态、权限、数据约束和目标版本。

## 可直接复制给 AI

```text
请把 {{功能范围}} 拆成可独立验收的用户故事，不拆技术任务、不写代码。

角色与目标：{{知道就写，或让 AI 从 PRD 提取}}
业务规则：{{知道就写，或让 AI 从 PRD 提取}}
状态与关键数据：{{由 AI 优先从材料/项目提取并标来源}}
权限和数据范围：{{产品描述业务可见性；技术映射由 AI/研发完成}}
本期非目标：{{列表}}

每个故事输出：
- 故事编号与名称；
- 作为谁、在什么场景、希望完成什么、获得什么价值；
- 前置条件与触发；
- Given/When/Then 验收标准；
- 权限不足、空数据、重复提交、并发修改、非法状态、超限、依赖失败等边界；
- 审计或通知要求；
- 依赖、风险、待确认项。

要求：一个故事只表达一个可观察结果；验收标准不得依赖实现细节；发现 PRD 冲突时先列冲突，不自行选择。
```

## 人工验收

检查每个故事能否独立演示和判定通过/失败；是否覆盖无权限、无数据、重复、失败和状态不允许；是否出现不同故事对同一状态或角色的矛盾描述。

## 停止条件

发现故事之间存在互斥业务规则时，停止拆分，输出冲突及其影响，交由产品负责人决定。
