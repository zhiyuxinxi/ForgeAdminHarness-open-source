# Forge Admin 阶段任务合同

Policy markers: `FORGE_TASK_CONTRACT_V2`, `PRODUCT_SAFE_DECISION_CARD_V1`, `ONE_ACTIVE_TASK_GUARD_V1`.

本 Skill 只固定当前项目、当前任务、当前阶段和动作权限。它不替代业务 PRD，也不把一次任务授权升级为长期偏好。

固定的是合同格式和权限规则，具体业务内容随本次需求动态生成。没有 Controller 阶段绑定的普通任务，按实际影响组织实现与验证；不用为新增菜单、改页面或修接口人为凑齐八阶段。`prepare_task` 可用时，在有限的代码定位后由模型提出本次范围，服务器核对原用户请求、项目允许范围、当前源码和实际文件依据，生成新的执行合同；旧合同及原拒绝记录保留。模型只提供业务目标、具体路径、职责与参考文件路径，不能指定身份、授权上限、摘要或执行代次。工具返回的任务信息供后续“继续”直接消费；明确只读和真实越权必须拒绝。

## 建立当前合同

1. 读取当前仓库的 `AGENTS.md`、`PROJECT_CONTEXT.md` 与平台注入的只读 Git 基线/工作区摘要；模型不得为取得这些事实调用任意 Git shell。只使用当前项目证据，不沿用其他项目或旧会话的运行信息。能访问 Harness 不等于使用者具备开发或运维职责；用户自述为产品/业务人员或明确表示看不懂技术内容时，进入产品友好模式。
2. 从用户当前表达与仍有效的唯一任务中确定动作级别：
   - 查看、分析、检查、评审、预检：只读；
   - 设计、整理、生成方案：只修改约定的文档；
   - 实现、修复、改代码：只修改当前已批准范围，未授权发布；
   - 测试、验证：运行约定测试；需要写测试数据时先说明范围和清理方式；
   - 发版、发布、上线：只授权当前项目受控发布，不授权补建基础设施或破坏数据；
   - 继续：继承同一仍有效任务的项目、范围和动作级别；下一环节已经属于原授权目标且前序证据满足时，直接衔接，不增加权限。组合请求如“修改后直接发版”按原请求已经明确授权的完整动作执行，不拆成逐步再次确认。
3. 在行动前形成一个简短合同，至少包含：项目/任务、当前基线、当前阶段、唯一目标、权威输入、范围、非目标、允许动作、禁止动作、业务决定责任人、技术复核责任人、验收证据和停止条件。
4. 若信息足够，直接在合同范围内工作；只有缺失内容会实质改变业务结果、权限或不可逆动作时才提出阻塞问题。实现授权包含完成该改动所必需、且位于当前机器合同 owned paths 内的最小编译与测试前置修复。不能仅因失败来自既有代码，就把修复退回给用户再次授权；先依据真实失败定位本任务的必要修复，再继续执行。补齐缺失的检查脚本仍须真实运行检查，不得用空脚本、跳过测试或放宽断言代替。

已授权完整目标内，完成一个环节后继续实现、必要检查、范围内修复、后台结果回收及已授权受控发布，不因阶段名称或工具等待要求用户回复“继续/下一步”。正式A9阶段保留各阶段产物与验收证据，通过现有Controller衔接下一已授权阶段，不能绕过当前机器合同。用户明确要求“先出方案，等我确认”时在该处等待；真实新增范围、缺失权限或需要业务决定时才提出具体问题。平台拒绝如有现成合法恢复路径则复用原候选、作业及有效回执恢复；无可用路径时报告具体缺陷，不把反复要求用户说“继续”当修复。

## 机器合同

Harness 会按真实写入路径生成 `Forge Task Execution Contract`，合同固定 `taskProfiles`、精确 `requiredSkills`、`tddRequired`、必跑 verification profiles、义务、semantic owner、repo-relative owned paths 与 action ceiling，并以 canonical hash 绑定。模型文字不能修改或提升这些派生字段。

- 普通开发按当前职责读取所需 Skill，复用本会话中未变化的相关内容；不为凑加载顺序反复读取。可信运行时仍启用正式阶段顺序时，按当前合同加载所需 pre-mutation Skill。`forge-evidence-truth` 帮助核对完成证据，加载动作本身不产生验证通过。
- 普通任务仅在可信运行时明确允许 `draftBeforeVerification`、当前身份/范围仍有效且动作级别为 `workspace-write` 时，才可先保存 owned paths 内的修复草稿；验证环境不可用不自行撤销这项既有写权限。只读请求、过期身份、越界路径及正式阶段要求仍须遵守，不能用 Skill 自行解锁写入。执行验证必须取得覆盖当前 profile 闭包的 ready admission，并在 `run` 中携带运行时注入的当前 `admissionId`；模型不得自行调用 `admit`、伪造租约或以逐 profile `capability` 替代准入。`cache_miss`、`cache_invalid` 或 unavailable 是验证环境阻塞，保留原因与已存草稿，不能声称验证通过、合入或发布，也不得退回直接 Maven/pnpm、下载依赖或换模型绕过。
- 新写入路径会单调扩展合同。扩展后新增的 Skill 与验证义务必须先满足，旧 receipt 不能覆盖新 diff。
- Bash 没有可靠的 typed owned path，不能用于源码、测试、配置或 Git 写入；使用结构化 `edit`/`write`。治理和验证命令必须是无管道、无重定向、无 PATH 覆盖、绑定 immutable base 的白名单 argv。
- 默认代码任务 ceiling 为 `workspace-write`。Git checkpoint 与 release 必须通过各自受控能力和独立授权，不能由 shell、Skill 文本或“继续”隐式提升。
- 合同或路径无法分类时失败关闭，先修正任务档案/范围，不尝试等价 shell 绕过。

## 产品友好决策接口

先把待决定事项分类，不能把所有不确定性都转交给产品人员：

- **业务决定**：角色、流程、字段含义、数据归属、状态规则、展示文案和验收结果。需要用户决定时，用“业务影响—推荐方案—替代方案—不决定的后果”说明，默认给一个有依据的推荐。
- **技术决定**：RSA/加密开关、API 建模方式、类/表实现、构建命令、缓存、迁移实现和部署机制。优先遵循项目权威、相似实现和技术门禁；存在高风险分歧时转交技术复核人，不要求产品人员在陌生术语中猜选。
- **平台阻塞**：项目身份、Runner、共享服务、权限或运行契约不可用。停止当前动作并给出结构化升级信息，不要求产品人员执行 Maven、pnpm、Docker、SQL、服务重启或“重新部署环境”。

面向产品/业务人员时，用自然短句说明发生了什么、对本次功能的影响、推荐方案及真正需要确认的业务问题；不强制固定标题或逐栏填表。信息足够且无需决定时直接继续工作，不必机械声明“无需产品人员操作”。技术证据保留在内部记录或后置按需附录，不把长日志作为决定界面。

不得要求业务人员取得、填写或解释 admission、RPC、HEAD、fingerprint、hash、Controller、TaskSpace、jobId 或 CLI 参数。必须由技术角色处理时，先说明受阻的业务步骤、实际影响和所需技术动作；升级卡作为内部记录或按需技术附录。只有存在真实派单、通知或接手证据时，才能说已由某位技术人员处理。

术语无法避免时，第一次出现立即给出业务含义。不要只把原技术说明换成更长的技术说明。

## 一个会话一个当前任务

- 当前动作运行期间收到新输入时，先判断它是同一目标的补充/纠正，还是新的交付物、阶段或权限。只有前者可以纳入当前合同。
- 新输入若改变唯一目标、进入原授权之外的阶段、要求尚未授权的发布或引入并行业务任务，不能静默合并或转向。先停在安全边界，报告当前任务状态、已发生写入和恢复点，再明确新任务或替换范围。同一已授权目标内的阶段衔接、需求补充和纠正不因这一条重新要求用户选择“替换当前任务”。
- 用户明确要求替换或停止时，先停止仍可停止的当前动作并保留证据；新合同不得继承旧任务的发布、数据写入或清理授权。
- 新消息本身不授权取消其他人的任务、重启 Harness、清理未知工作区或处理其他分支。

## Forge 路由

- 任何 Forge 源码、SQL、API、前端、流程、安全或测试任务先用 `forge-task-router` 按真实 changed paths 和风险选择最小组合；不能只凭用户一句“改页面”忽略后端、权限或迁移影响。
- CRUD、表、API、菜单、权限或 Excel 任务：先按实际影响加载需要的数据库、后端、前端、安全或测试 Skill；普通任务通过 `prepare_task` 形成本次合同。只有已绑定 Controller 正式阶段状态时，才用 `forge-crud-production` 形成对应阶段合同，并在 `domain-contract` 阶段完整读取存在的 `.agents/skills/forge-codegen-crud/SKILL.md`。不得为了“覆盖完整”在单轮中同时加载全部领域 Skill。项目 Skill 负责当前业务细节，Harness Skill 和 `forge-governance` 提供不可下调的最低线。
- 审批、Flowable、流程表单或业务回调：若存在 `.agents/skills/forge-business-flow-development/SKILL.md`，完整读取，并加载 `forge-workflow-production`；状态字段不能冒充真实流程。
- 字典/枚举使用 `forge-dictionary-contract`；页面或弹窗一致性使用 `forge-ui-consistency-review`；发布使用 `forge-controlled-release`；发布后业务验收使用 `forge-release-acceptance`。

## 防偏航规则

- 用户只要求合同、方案或检查时，不修改业务代码、提交、发布或持久化 Memory。
- 阶段完成不产生新的权限；下一阶段已被原完整目标授权且前序证据满足时应继续，不追加人工确认。`verified`、`committed`、`released` 是不同状态，分别保留实际证据。
- 发现与本任务无关的缺陷时记录为建议或阻塞，不顺手修复；直接阻断当前已授权交付的必要前置修复按当前合同处理。所需路径不在 owned paths 内时如实报告具体缺口，不自行改写授权。发现他人未提交改动时不清理、不覆盖、不纳入本轮提交。
- 必要前置修复已属于同一用户目标、但旧合同遗漏直接相关测试或迁移路径时，先依据失败回执与实际文件提出最小路径集，通过可用的 `prepare_task` 请求受保护合同续接。保留旧拒绝与有效回执，由服务器核定新范围；不能自行扩大 owned paths，也不能只说“文件未授权”就结束仍可合法推进的修复。只有恢复入口确实拒绝或所需动作超出原用户授权时，才报告具体阻塞。
- 发生过文件写入、测试数据写入、提交或发布时，结果必须逐项如实报告，不得再声称“全程只读”。
- 不把“请你运行以下命令”作为面向产品/业务人员的失败恢复。必须由技术人员处理的动作只生成升级卡，包含目标项目、阶段、证据、影响、建议责任人和恢复前置条件。

## 输出

本次形成或使用业务定义、设计、实现及验证依据时，读取并遵循[过程产物约定](references/delivery-center-artifacts.md)；已读取且未变化的内容直接复用。在当前已授权产物中同步保留实际形成或使用的功能目标、可观察结果、边界、菜单/功能引用、字段规则、操作、接口调用和真实来源，供后续 AI 定位原定义与具体修订继续工作，也供中心阅读。协议字段可选是为了兼容旧产物，不表示本次已经明确且用于交付的内容可以省略。不另写展示台账、不为填表编造、不增加顶层 payload 字段、阶段或完整率门禁，也不重做未改上游；未变化的已有定义保留引用即可，功能关联允许单向记录后由平台反查。

默认使用用户的主要语言，以 1–3 个简短段落或确有必要的短列表，先讲本次具体业务结果和当前影响，必要时给实际下一步。最终仍要准确区分已做、未做、验证结果、剩余阻塞，以及当前动作是否产生文件写入、测试数据、Git 提交或发布；这些机器事实完整记录，必要技术细节放在后置证据区，不在首屏逐项转储。
